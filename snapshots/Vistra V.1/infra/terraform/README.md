# VISTRAH AWS staging infrastructure

Terraform here describes a separate staging environment for the existing VISTRAH containers. It does not modify `infrastructure/terraform` (the existing dev S3/log configuration), local Docker Compose, or any database. This is infrastructure preparation: **do not run `terraform apply` until the plan and cost have been explicitly reviewed and approved.** Payments are forced to sandbox.

## Prerequisites

- Terraform 1.6 or later (validated with 1.14.4).
- AWS CLI v2 and an AWS identity with permissions limited to the reviewed staging resources. Configure with SSO/profile rather than storing static keys in this repository.
- Docker, and a confirmed AWS account, billing owner, and `ap-south-1` region.
- Two available AZs and a CIDR range that does not overlap connected networks.
- Reviewed immutable web/API images in the two staging ECR repositories before starting ECS tasks.
- An approved staging hostname and existing Route 53 public hosted-zone ID if HTTPS/DNS is wanted. Terraform never discovers or creates a hosted zone automatically.

AWS CLI checks:

```powershell
aws --version
aws sts get-caller-identity
aws configure list
```

No AWS credentials were available during preparation. Do not add credentials to `.tfvars`, shell scripts, or source control.

## Configuration

The default region is `ap-south-1`; the default network is `10.20.0.0/16`. Two AZs are selected dynamically by the AWS provider. Set `availability_zones` only if you need specific AZs. Copy `terraform.tfvars.example` to an untracked `terraform.tfvars` and fill in the reviewed image URIs and optional domain values. Do not put secret values there.

The frontend reads `NEXT_PUBLIC_API_URL` in client code, and Next.js bakes that value into the web image at build time. Build the web image with `--build-arg NEXT_PUBLIC_API_URL=https://<hostname>/api/v1` (or the ALB URL before DNS exists); setting a container runtime variable alone cannot change the already-built browser bundle. The API receives the public origin through `CORS_ORIGINS`.

The initial configuration creates a VPC with two public, two private app, and two isolated private database subnets; one NAT gateway; ALB; private ECS/Fargate services; private encrypted PostgreSQL 16 RDS; two ECR repositories; IAM roles; log groups; and Secrets Manager secret resources. RDS accepts port 5432 only from the API security group. Ports 3000, 8000, and 5432 have no public ingress.

RDS password, JWT secret, and payment webhook secret are generated by Terraform and delivered to Secrets Manager/ECS without being printed as outputs. Terraform state will contain sensitive generated values; protect local state, do not commit it, and use an approved encrypted remote state backend before team use. The provider/payment credential secret is created as an empty container and is not used by the sandbox adapter. Do not populate it with real credentials in this phase. Sandbox mode is set in ECS task environment and remains enforced.

## Format, initialize, validate, and plan

From this directory:

```powershell
terraform init
terraform fmt -recursive
terraform validate
terraform plan -out=staging.tfplan
terraform show staging.tfplan
```

Review the complete plan, account ID, region, IAM, network exposure, Secrets Manager changes, and cost before asking for apply approval. No apply is run by this preparation. Never share a saved plan or state file because they may contain sensitive values.

## Images and ECS deployment (later)

1. Build and review images locally. For the web build, use the public staging API URL as `NEXT_PUBLIC_API_URL` build argument.
2. Authenticate Docker to the ECR URLs in Terraform outputs using `aws ecr get-login-password`, tag images with immutable release tags, and push them. No image is pushed by Terraform.
3. Set `web_image` and `api_image` in untracked `terraform.tfvars`, run and review a fresh plan, and only after explicit approval apply it.
4. For a new release, push a new immutable tag, update the image variables, review the plan, and apply through the approved release process. ECS uses `/` for web health and `/health` for API health.

## DNS and HTTPS (optional until domain approval)

With both `staging_hostname` and the ID of the correct existing public hosted zone set, Terraform requests an ACM DNS-validated certificate, adds only the certificate validation CNAME and staging A alias, waits for validation, attaches HTTPS, and redirects HTTP to HTTPS. Without both inputs, the public ALB serves HTTP and routes `/api/*` to the API; it will not create or guess DNS records. Confirm the hosted zone and record ownership before planning these resources.

## Database migration (separate later operation)

No migration is run by this Terraform. The current application schema and local data are not copied to RDS. After infrastructure is approved and created:

1. Confirm the RDS endpoint is private and test connectivity from the API task in the VPC.
2. Review the migration set for staging; create a backup/snapshot and an explicit rollback plan.
3. Run the approved migrations as a separate controlled job/task, never from Terraform or automatically at API startup.
4. Seed only approved staging data; do not copy the local database or production data automatically.
5. Verify API health, authentication, public pages, admin workflows, database access, and sandbox payment/webhook behavior.
6. Plan any real-data migration as a separate security, privacy, and business-approved project.

## State, cost, and teardown

The initial backend is local. Before shared/team use, approve an encrypted S3 state bucket, versioning, restricted access, and a locking design compatible with the team's Terraform version. Do not create an S3 backend or lock table until account/bucket ownership is confirmed.

Major always-on cost drivers are the NAT gateway (AWS lists $0.045/hour plus processing in its pricing example, roughly $33/month at 730 hours before data), the ALB (hourly charge plus LCU and public IPv4), two running Fargate tasks, RDS plus storage/backups, and CloudWatch ingestion/storage. One NAT gateway saves hourly cost versus one per AZ but introduces an AZ dependency and cross-AZ traffic charges. RDS is a small single-AZ `db.t4g.micro`, but it is still billed continuously. ECR storage, Secrets Manager, data transfer, snapshots, taxes, and free-tier eligibility also affect totals. Use the AWS Pricing Calculator for the selected region/account before approval; these are not a quote. [VPC pricing](https://aws.amazon.com/vpc/pricing/), [ALB pricing](https://aws.amazon.com/elasticloadbalancing/pricing/), [Fargate pricing](https://aws.amazon.com/fargate/pricing/).

To destroy staging safely, first stop/review ECS workloads and backups, take an approved final RDS snapshot, change `db_deletion_protection` to `false`, choose a unique `db_final_snapshot_identifier`, review the destroy plan, and obtain explicit approval. Destroy only this workspace/state. Secrets Manager has a recovery window, and retained snapshots/ECR images can continue to incur charges; review them separately. Never use `-auto-approve`.

## Explicitly not implemented

- No AWS resources have been created or changed by this preparation.
- No Terraform apply, image push, database migration, DNS change, live payment, or production sizing.
- No production payment adapter or payment credentials. Only the existing sandbox payment mode is configured.
- No remote state bucket/lock service, autoscaling, WAF, or cross-AZ NAT gateways.
